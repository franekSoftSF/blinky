# 13 — Passkey provisioning

A YubiKey can carry two credentials for one person: a PIV certificate for
Windows sign-in, which the rest of these documents are about, and a FIDO2
passkey for a cloud identity provider. This document is the operator's half of
the second: what Blinky does, what has to exist at Microsoft Entra ID or Okta
before it can, what leaves the network, and what does not exist yet.

The design is [12 — the brief](12-passkey-provisioning-brief.md); the patches
are Phase 7 in [07](07-roadmap.md#phase-7--fido2-on-the-same-key). The
semantics of every provider call were ported from
[KeyEnroll](https://github.com/inowakowski/KeyEnroll) (MIT), which has registered
a passkey with Okta on real hardware.

> **State, 2026-10-09.** Everything below is built, unit-tested and deployed on
> BY-CACMS. **None of it has met a real Entra tenant, a real Okta org, or a key
> through the FIDO interface.** The prerequisites in this document are written
> from the providers' documentation and KeyEnroll's, not from a walk through a
> tenant. The first one to be walked through will correct this page; until then
> treat a menu name here as a pointer, not a promise.

## What happens

```
 operator (console)          api                    provider            workstation (agent, LocalSystem)
 ──────────────────          ───                    ────────            ───────────────────────────────
 /passkeys: user, key,  ─►   resolve the user ──►   GET user
 workstation, PIN policy     job + PasskeyCredential row (Requested)
                                                                        claims the job, opens the key over HID
                                                                        sets / changes the FIDO2 PIN,
                                                                        minimum length                     (KeyReady)
                        ◄──  Fido2Ready ◄─────────────────────────────── 
                             begin registration ─►  challenge, rp, user
                        ───  Fido2CeremonyRequest ─────────────────────► clientDataJSON, makeCredential, touch
                                                                                                           (ChallengeIssued)
                        ◄──  Fido2CeremonyResult ◄──────────────────────
                             check clientDataJSON
                             (Provisioned) register ─► accept attestation
                        ───  Fido2Registered ──────────────────────────► forceChangePin on the key
 /passkeys shows each   ◄──  (Registered)
 step as it happens
```

The ceremony runs in the agent and never in the browser: the provider dictates
the relying party - `login.microsoft.com`, or the Okta org's domain - and a
browser refuses a ceremony for a relying party that is not the page it is on.
The agent never speaks to a provider either. It is told rpId, origin and
challenge, and answers with what the key produced; every provider call is made
by the `api` container.

The same page issues the PIV card onto the same key (0052's dialog, opened with
the token, the agent that last saw it and the person searched by this user's
login), so one key leaves the desk with Windows sign-in and the passkey.

## Configuring a provider

**Administration → Passkey providers**, administrators only. Providers are rows
in the database (0107); nothing about them is in `.env` or
`docker-compose.yml`, and a deployment with none configured makes no call to any
cloud.

A provider's name and kind are fixed once created - passkey rows name their
provider - and a provider through which passkeys are registered is disabled, not
deleted.

The credential Blinky reaches the provider with is generated by Blinky by
default, and that is the recommended route:

| Provider | Generated | Shown in the console | Given to the provider |
|---|---|---|---|
| Entra | RSA 2048 self-signed certificate, two years | The certificate (PEM) and its SHA-1 thumbprint, as the portal lists it | Uploaded under the app registration's *Certificates & secrets* |
| Okta | RSA 2048 key | The public JWK with an RFC 7638 `kid` | Added to the service app's public keys |

The private half is made, sealed and used on the server and never reaches a
browser. A credential can be imported instead - a PEM or PFX certificate or an
Entra client secret (with its *Secret ID* and expiry, as the portal shows them),
an Okta private key or API token - and is sealed on arrival and never returned.
**Test connection** asks the provider for a user who does not exist and reports
what it answered; a refused token, a missing consent or a wrong URL shows there
rather than at the first ceremony.

## Microsoft Entra ID

What the tenant needs:

1. **An app registration.** The *Directory (tenant) ID* and *Application
   (client) ID* from its overview go into the provider form.
2. **Microsoft Graph application permissions**, with admin consent:
   `UserAuthenticationMethod.ReadWrite.All` (create, list and delete FIDO2
   methods on users) and `User.Read.All` (find the user by UPN or mail).
   Application, not delegated: Blinky calls as itself, with client credentials,
   and keeps the record of which operator asked in its own audit trail.
3. **A credential**: the certificate Blinky generates, or a client secret. A
   secret expires - at most two years - and Entra offers no API to ask when;
   the console marks one within thirty days of the expiry it was given.
4. **The passkey method enabled for the users**: *Authentication methods →
   Policies → Passkey (FIDO2)*, enabled for a group the test users are in. If
   the policy restricts keys or enforces attestation, the YubiKey model's AAGUID
   has to be allowed; the agent reports the AAGUID of the key it opened, and the
   attestation object is passed to Entra exactly as the key produced it.
5. **A cloud user**, not a B2B guest - Graph does not register FIDO2 methods for
   guests.

Graph v1.0 is called (brief 12 assumed beta; KeyEnroll uses v1.0 and so does
Blinky). The challenge lifetime asked for is the provider's *challenge lifetime*
setting, 5 to 60 minutes; it is also the deadline the ceremony has to finish by.

For a lab tenant, an Entra ID tenant created with an Azure subscription, or a
Microsoft 365 developer sandbox where one is available, has everything above.
Whether a particular licence tier is required for on-behalf FIDO2 registration
is not established here and is one of the things the first walk-through will
answer.

## Okta

What the org needs (Okta Identity Engine; Classic Engine is out of scope):

1. **The org URL users sign in at** - the default `*.okta.com` domain or the
   custom one. Credentials are bound to the domain they are created on, so this
   is the sign-in domain, not the admin one.
2. **An API service app** with client credentials and *public key / private
   key* client authentication, holding the JWK Blinky generated. **DPoP off**
   ("Require Demonstrating Proof of Possession"): Blinky does not send DPoP
   proofs, and a token refused for that reason says so.
3. **Granted scopes**: `okta.users.read` and `okta.users.manage`, the pair
   KeyEnroll uses.
4. **An admin role assigned to the service app.** Okta checks the app's role as
   well as its scopes before it lets the app manage users' factors; a
   super-administrator role is the quick answer for a lab and a narrower custom
   role the answer for anything else.
5. **The FIDO2 (WebAuthn) authenticator** enabled, and an enrolment policy that
   allows it for the users concerned. Okta caps the number of WebAuthn factors
   per user (of the order of ten).

An SSWS API token also works and is meant for a lab only: it acts as the admin
who made it and does not expire on its own.

An Okta Integrator (developer) org is free and has all of the above. Okta is the
one provider where the flow has been proved on hardware - by KeyEnroll, with the
same calls, not yet by Blinky.

## What leaves the network

Only the `api` container, and only once a provider is configured:

| Destination | Why |
|---|---|
| `login.microsoftonline.com` (or the national-cloud authority set on the provider) | Client-credentials token |
| `graph.microsoft.com` (or the national-cloud Graph endpoint) | Users, FIDO2 methods |
| The Okta org URL | Token and the Users / Factors API |

Nothing else in the stack gains any egress: the worker, the console, the edge
and PostgreSQL stay where they were, and the workstation agent talks to the
Blinky API and to the key and to nothing else. A deployment that configures no
provider makes no outbound call at all.

## Chain of custody

A key that leaves the desk with a registered passkey and a provisional PIN is a
**live credential in transit**: whoever holds both can sign in as its owner.

- The provisional PIN is generated on the workstation, shown **once** in the
  agent's window, and is in no message, no column and no log - the API has no
  field for it (0074) and the console says only whether one was set. If it is
  lost before it reaches the holder, the way back is a FIDO reset, not a lookup.
- Ship the key and the PIN by **different channels**, and record the key's
  serial against its holder (the passkey row does: serial, AAGUID, provider and
  method id).
- Leave **force PIN change** on, so the first use replaces the PIN the operator
  saw. It is set only after the provider has accepted the credential; keys
  without CTAP 2.1 cannot be told to, and the job says so.
- A key lost in transit is revoked from **/passkeys**: deleted at the provider
  first, marked in Blinky second, never the other way round.

## Google Workspace

There is **no public Google API that accepts a passkey registered on a user's
behalf**; users enrol their own security keys. Blinky shows Google in the
provider list, disabled, with that reason, rather than leaving its absence to be
read as a configuration gap.

Two things are possible instead. A *prepare-only* key - FIDO2 PIN set with a
forced change, serial recorded against the holder - which the user then enrols
at Google themselves; analysed in brief 12 §7 and not built. And federation:
Google Workspace delegating sign-in to Entra or Okta over SAML, so the passkey
Blinky registers there is the one that signs the user into Google too. Where an
organisation already federates, the second is the answer, and it needs nothing
from Blinky.

## When it goes wrong

| What you see | What it means |
|---|---|
| *Test connection*: `AADSTS700016` | The application (client) ID does not exist in that tenant |
| *Test connection*: `AADSTS7000215` / `invalid_client` | The secret or certificate is not the one the app registration holds |
| *Test connection*: Graph `403 Authorization_RequestDenied` | Permissions missing or admin consent not granted |
| *Test connection*: Okta token refused mentioning DPoP | Turn off "Require Demonstrating Proof of Possession" on the service app |
| A ceremony fails with `challenge-expired` | The person took longer than the challenge lifetime; the agent asks for a new one on the next attempt |
| *Missing at provider* on a passkey | Registered by Blinky, deleted at the provider since - by an administrator there, or a UPN change in Entra |
| *Provider only* on a passkey | At the provider, not made by Blinky - a key the user enrolled themselves |
| An Okta factor `PENDING_ACTIVATION` in the list | A ceremony that was started and not finished; a job expired by the watchdog does not clean this up yet |
| The agent says the FIDO interface needs elevation | Windows opens FIDO HID only to elevated processes; the service runs as LocalSystem for this reason ([08](08-hardware-notes.md#fido2-over-hid)) |
| Two keys plugged in and the job names none | Refused on purpose; leave only the key to provision |

## Not built yet

- **0070** - FIDO2 state in the inventory, joined to the PIV token by serial.
- **0072** - a FIDO PIN change or FIDO reset as a job of its own, with a
  confirmation that names how many passkeys a reset destroys.
- Cleanup of a provider-side pending registration when the watchdog, rather
  than the agent, ends the job.
- **0073b** - Okta's preregistration API, where Okta mails the PIN to the user.
- A passkey request raised from the workstation and approved in the console
  (in progress in another session; its patch number is being settled).
