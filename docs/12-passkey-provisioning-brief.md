# Brief — Passkey (FIDO2) provisioning on behalf of users: Microsoft Entra ID + Okta (+ Google Workspace analysis)

**Project:** Blinky (https://github.com/franekSoftSF/blinky)
**Feature:** Register FIDO2 credentials on YubiKey 5 on behalf of directory users — **Microsoft Entra ID and Okta** — from the existing web console, using the existing workstation agent.
**Audience:** Claude Code, working inside the Blinky repository. Follow existing repo conventions everywhere: central package versions in `Directory.Packages.props`, job envelopes in `Blinky.Contracts`, NHibernate mappings with schema generated by `tools/SchemaTool`, Serilog, docs numbered under `docs/`.
**Version:** v3 — Okta as a second provider behind the same abstraction (Phase A: Entra, Phase B: Okta; the agent-side ceremony is identical for both), plus an **analysis section for Google Workspace (§7)** where full on-behalf registration is not possible today — read §7 before assuming anything about Google, and do not implement any Google code unless the optional prepare-only phase (Phase C) is explicitly requested.

---

## 1. Goal

An operator opens the Blinky console, picks a directory user, plugs a YubiKey into a workstation running the Blinky agent, and the system:

1. asks the identity provider (Entra ID via Microsoft Graph, or Okta via its management API) for WebAuthn creation options for that user,
2. performs the CTAP2 `makeCredential` ceremony on the YubiKey (touch + FIDO2 PIN),
3. posts the attestation back to the provider, registering the passkey directly in the user's account,
4. optionally sets a **provisional FIDO2 PIN** with `forceChangePin` so the user must change it on first use,
5. records the credential in the Blinky database with a full audit trail, and supports later revocation (delete on the provider API).

The key ships to the user and works on day one — no self-registration, no Temporary Access Pass.

## 2. Non-goals (this iteration)

- No browser-side WebAuthn. `navigator.credentials.create()` **cannot** be used: the provider dictates the rpId (`login.microsoft.com` for Entra, the org's Okta domain for Okta) and the browser enforces rpId == page origin. The ceremony happens **only** in the agent.
- **No Google Workspace registration.** Google exposes no public API to register a passkey/security key on behalf of a user — see the full analysis and the optional prepare-only concept in §7. Nothing from §7 is implemented unless Phase C is explicitly requested; the provider abstraction must merely not preclude it.
- No support for non-YubiKey authenticators (consistent with the rest of Blinky).
- No bulk/batch provisioning UI (design the job contract so batching is possible later, but build single-key flow only).
- No B2B guest users on Entra (unsupported by the Graph API).
- No synced passkeys / authenticator apps — hardware security keys only.
- No Okta "third-party fulfillment" logistics (Yubico ships pre-programmed keys); Blinky **is** the fulfillment — see §6.3 for how the Preregistration API is optionally used anyway.

## 3. Provider-neutral design rule (read first)

Everything provider-specific lives behind one interface; everything ceremony-specific is provider-agnostic. Concretely:

- **rpId and origin are per-provider, per-tenant data — never constants.** `clientDataJSON.origin` for Entra is `https://login.microsoft.com`; for Okta it is `https://<org>.okta.com` (or the org's custom domain, exactly as returned/configured). The agent receives rp + origin in the job payload and must not hardcode either.
- The agent-built clientDataJSON is identical in shape for both providers:

```json
{"type":"webauthn.create","challenge":"<challenge exactly as received, base64url>","origin":"<per-provider origin>","crossOrigin":false}
```

`clientDataHash = SHA-256(UTF8(clientDataJSON))` is the input to CTAP2 `makeCredential`.

- Field-name differences (Graph vs Okta JSON) are normalized in the provider implementation into one internal `PasskeyCreationOptions` model before anything reaches `Blinky.Contracts`.

## 4. Component map

### 4.1 New class lib: `Blinky.Passkeys` (mirrors the `Blinky.Pki` pattern: one interface, multiple backends)

- `IPasskeyDirectory`:
  - `GetCreationOptionsAsync(userRef, TimeSpan timeout) → PasskeyCreationOptions` (normalized: challenge, rpId, origin, user handle/name/display, pubKeyCredParams, excludeCredentials, authenticatorSelection, attestation preference, deadline)
  - `RegisterAsync(userRef, RegistrationPayload) → RegisteredPasskey` (provider method id, created timestamp)
  - `ListAsync(userRef)`, `DeleteAsync(userRef, providerMethodId)`
  - `Capabilities` (flags: PinDeliveryByProvider, SupportsDriftList, …) so the UI can adapt per provider.
- `EntraPasskeyDirectory` — Microsoft Graph beta implementation (§5).
- `OktaPasskeyDirectory` — Okta management API implementation (§6).
- Shared: token acquisition + caching, retry with backoff on 429/5xx, defensive JSON parsing (log + surface raw payload on failure), clean error mapping.
- User mapping resolver per provider: Blinky cardholders (AD/Samba4) → Entra objectId (default: UPN match, cache objectId) and → Okta userId (default: login/email match, cache id).

### 4.2 `Blinky.Contracts` — new job envelope (provider-agnostic)

New job type `ProvisionFido2Credential`, plus a protocol **version bump** per repo rules. Two-phase shape (challenge TTL forces this):

1. `Fido2PrepareRequest` (backend → agent): reader hint, expected serial (optional), PIN policy `{ mode: OperatorSets | ProvisionalRandom | ProviderDelivers, minPinLength, forceChangePin }`.
2. `Fido2Ready` (agent → backend): serial, firmware, FIDO2 applet state (PIN set?, retries, free resident slots), AAGUID.
3. `Fido2CeremonyRequest` (backend → agent): the normalized `PasskeyCreationOptions` **including rpId and origin**, constructed after `Fido2Ready`, immediately after calling the provider.
4. `Fido2CeremonyResult` (agent → backend): `credentialId`, `attestationObject`, `clientDataJSON`, AAGUID, serial, whether a provisional PIN was set (and the PIN value **only** when policy is `ProvisionalRandom` and the operator must see it once — see §9).
5. Terminal statuses reuse the existing job state machine; add FIDO2-specific failure codes (§10).

The envelope carries no provider identifier semantics beyond an opaque `directoryProvider` tag for audit — the agent behaves identically for Entra and Okta.

Idempotency: `excludeCredentials` prevents duplicate registration of the same key for the same user on both providers; additionally the agent must treat a repeated `Fido2CeremonyRequest` with the same challenge as the same operation.

### 4.3 `Blinky.Agent.Service` — the ceremony executor (unchanged between providers)

- Add package `Yubico.YubiKey` (Yubico .NET SDK). The FIDO2 applet over USB is **HID, not PC/SC** — enumeration is separate from the existing reader watcher. Correlate HID device ↔ PC/SC card by YubiKey serial.
- Windows restricts raw FIDO HID access to elevated processes; `Agent.Service` runs as LocalSystem, so this is satisfied. Document it; fail with a clear error if access is denied.
- Use `Fido2Session`:
  - read applet info (`AuthenticatorInfo`): AAGUID, options, minPinLength, remaining resident credential slots, PIN retries;
  - if no PIN set and policy requires one: `SetPin` (operator-entered via Agent.Ui prompt, or generated provisional PIN);
  - CTAP2.1 when supported: `SetMinPinLength`, `forceChangePin` after setting the provisional PIN;
  - `MakeCredential` with: `clientDataHash` (agent-built, §3), rp, user, algorithms from `pubKeyCredParams` (ES256 first), `excludeCredentials`, resident key per `authenticatorSelection` (both providers use discoverable credentials — expect rk true), UV per options.
  - Touch prompt: fire the existing named-pipe notification to `Agent.Ui` ("touch your key") when the SDK signals user presence is pending; PIN entry likewise reuses the existing PIN prompt with a clear label that this is the **FIDO2 PIN, distinct from the PIV PIN**.
- Serialize `attestationObject` exactly as produced (CBOR, base64url) — do not re-encode.

### 4.4 `Blinky.Domain` + `Blinky.Infrastructure`

- New entity `PasskeyCredential`: id, cardholder ref, card ref (serial), **directoryProvider (Entra | Okta)**, provider user id + login/UPN snapshot, provider method/factor id, credentialId (base64url), AAGUID, displayName, attestation blob (for audit), created/registered/revoked timestamps, state.
- State machine: `Requested → KeyReady → ChallengeIssued → Provisioned → Registered → Revoked` (+ `Failed` with reason). Follow the pattern of the existing three state machines. Okta preregistration fulfillment statuses (§6.3) map into `Provisioned/Failed`.
- NHibernate mapping + regenerate schema via `tools/SchemaTool`; both services' startup schema comparison must pass.
- Provisional PIN is **never stored**. It exists only in the job result in transit and in the UI once (§9) — or never touches Blinky at all when the provider delivers it (Okta preregistration email, §6.3).

### 4.5 `Blinky.Api` + frontend (Angular)

- REST: create/inspect/cancel provisioning jobs; list passkeys per cardholder/card (merge local DB + live provider list for drift detection); revoke (delete at provider, then mark local). All provider calls happen server-side; the agent never talks to Entra or Okta.
- SignalR orchestration: on `Fido2Ready`, call `IPasskeyDirectory.GetCreationOptionsAsync`, immediately dispatch `Fido2CeremonyRequest`; on `Fido2CeremonyResult`, call `RegisterAsync`, persist, complete job. Enforce the challenge deadline as a job-level timeout.
- Angular: "Passkey" panel on the token/cardholder view — **provider selector** (only configured providers shown), user picker with resolved provider identity, PIN policy selection (options constrained by provider `Capabilities`), live ceremony status (waiting for key / touch / PIN / registering), result screen. Passkey list with provider badge, revoke action, and drift badge when provider and DB disagree.

### 4.6 Configuration & deployment

- `.env.example`:
  - Entra: `ENTRA__TENANTID`, `ENTRA__CLIENTID`, `ENTRA__CLIENTCERTPATH` / `ENTRA__CLIENTSECRET`, `ENTRA__CHALLENGETIMEOUTMINUTES`.
  - Okta: `OKTA__ORGURL` (e.g. `https://acme.okta.com` — also the source of rpId/origin unless overridden), `OKTA__AUTHMODE` (`ApiToken` | `OAuthPrivateKeyJwt`), `OKTA__APITOKEN` (secret ref) or `OKTA__CLIENTID` + `OKTA__PRIVATEKEYPATH`, `OKTA__USEPREREGISTRATIONAPI` (bool, default false).
- Either provider may be absent; the feature degrades gracefully (provider hidden in UI with reason).
- Docker: `api` (and only `api`) needs egress to `graph.microsoft.com` + `login.microsoftonline.com` and/or the Okta org URL. Note this in the network docs — the rest of the stack remains fully on-prem.

## 5. Provider: Microsoft Entra ID (Phase A)

Microsoft Graph **beta** endpoints (public preview — isolate behind the interface, expect churn):

```
GET  https://graph.microsoft.com/beta/users/{id|upn}/authentication/fido2Methods/creationOptions(challengeTimeoutInMinutes={n})
POST https://graph.microsoft.com/beta/users/{id|upn}/authentication/fido2Methods
GET  https://graph.microsoft.com/beta/users/{id|upn}/authentication/fido2Methods
DELETE https://graph.microsoft.com/beta/users/{id|upn}/authentication/fido2Methods/{methodId}
```

- Auth: **client credentials** (application permission `UserAuthenticationMethod.ReadWrite.All`, admin-consented). Prefer certificate credential (`Azure.Identity` / MSAL confidential client); support secret for labs.
- `creationOptions` returns a `publicKey` object shaped like WebAuthn `PublicKeyCredentialCreationOptions`; rp.id is `login.microsoft.com`, origin for clientDataJSON is `https://login.microsoft.com`.
- The **challenge TTL** equals `challengeTimeoutInMinutes` requested — fetch options only after `Fido2Ready`.
- Registration POST body:

```json
{
  "displayName": "<e.g. 'YubiKey 5C NFC #<serial>'>",
  "publicKeyCredential": {
    "id": "<base64url credentialId>",
    "response": {
      "clientDataJSON": "<base64url>",
      "attestationObject": "<base64url>"
    }
  }
}
```

- Reference implementations of this exact flow: YubicoLabs `entraId-register-passkeys-on-behalf-of-users` (Python) and `DSInternals.Passkeys` / `DSInternals.Win32.WebAuthn` (C#). Mirror their semantics, not their architecture.

**Tenant prerequisites** (document + pre-flight-check where possible): FIDO2 method enabled for the target user (group scoping); AAGUID allow-list must include the key model; attestation enforcement tolerated (YubiKey packed attestation chains to the Yubico FIDO CA — pass `attestationObject` through untouched); not available for B2B guests; UPN change invalidates the method (detect via drift check).

## 6. Provider: Okta (Phase B)

Okta supports on-behalf enrollment natively (the Admin Console has a manual "Enroll FIDO2 Security Key" action; Blinky automates the API equivalent). Two API routes — implement 6.2 as the default, 6.3 as an optional mode.

### 6.1 Common Okta facts

- **rpId / origin**: the org's Okta domain (`https://<org>.okta.com` or the org's custom domain). Derive from `OKTA__ORGURL`; always prefer the rp values returned by the API itself over configuration when present.
- Auth: SSWS API token (simple, labs) or **OAuth2 service app with `private_key_jwt`** and the relevant Okta management scopes for user/factor administration (verify exact scope names against current Okta docs at implementation time — they evolve). Prefer OAuth2 for production; token never logged, stored via secrets-at-rest.
- Okta Identity Engine assumed. Document that Classic Engine orgs are out of scope.
- Per-user WebAuthn enrollment cap exists (order of ~10); surface a friendly error when hit.

### 6.2 Default route — admin enrollment via Factors API

Same three-step shape as Graph:

1. `POST /api/v1/users/{userId}/factors` with `{"factorType":"webauthn","provider":"FIDO"}` → response contains the factor id (status `PENDING_ACTIVATION`) and embedded **activation** object = WebAuthn creation options (challenge, rp, user, pubKeyCredParams, excludeCredentials…). Normalize into `PasskeyCreationOptions`.
2. Agent ceremony (§4.3) with origin = org URL.
3. `POST /api/v1/users/{userId}/factors/{factorId}/lifecycle/activate` with the base64url `attestation` (attestationObject) and `clientData` (clientDataJSON). Success → factor `ACTIVE`; store factor id as the provider method id.

List/delete for lifecycle + drift: `GET /api/v1/users/{userId}/factors`, `DELETE /api/v1/users/{userId}/factors/{factorId}`.

Note the naming difference vs Graph (`attestation`/`clientData` vs `attestationObject`/`clientDataJSON`) — keep the mapping inside `OktaPasskeyDirectory`; the contracts stay neutral.

Challenge TTL: Okta activation challenges are short-lived like Graph's; enforce the same job deadline. If the factor is left `PENDING_ACTIVATION` after a failed/expired ceremony, **delete the pending factor** during job cleanup so retries start clean.

### 6.3 Optional route — WebAuthn Preregistration API (`OKTA__USEPREREGISTRATIONAPI=true`)

Okta's Preregistration API is built for fulfillment providers (Yubico's ship-a-programmed-key program); its endpoints live under `/webauthn-registration/api/v1/…` and cover initiating enrollments, submitting them, PIN delivery, and fulfillment status transitions (including error marking). Two properties make it attractive even with Blinky as the "fulfillment provider":

- **PIN delivery by Okta**: the provisional PIN is emailed to the end user via the customizable `WebAuthnPreRegistrationPin` template — the PIN then never needs to surface in the Blinky UI at all (`Capabilities.PinDeliveryByProvider = true`, PIN policy mode `ProviderDelivers`).
- Fulfillment statuses map naturally onto the `PasskeyCredential` state machine (mark-error → `Failed`).

Caveats: the API may require an Early Access feature flag on the org and its contract is aimed at Yubico's flow — implement it behind the same `IPasskeyDirectory`, feature-flagged, verified against a live org before enabling by default. If it proves impractical, the Factors route (6.2) plus Blinky's own one-time PIN display covers the same need.

### 6.4 Okta tenant prerequisites

Passkeys/FIDO2 (WebAuthn) authenticator enabled in the org; enrollment policy permits the target user/group; if the org enforces authenticator allow-lists/attestation, the YubiKey AAGUID must be permitted; custom domain (if any) known to Blinky so origin matches.

## 7. Provider: Google Workspace — analysis only (Phase C: optional, decision pending)

**Do not implement anything from this section unless Phase C is explicitly requested.** It exists so the design keeps the door open and so `docs/13-passkey-provisioning.md` can explain the gap honestly to operators.

### 7.1 Why full provisioning is impossible today

- Google Workspace has **no public API that accepts a WebAuthn attestation on behalf of a user**. Passkey/security-key enrollment happens only inside the end user's own authenticated web session at `myaccount.google.com` (rpId `google.com`).
- This is not an agent limitation: the Blinky agent could perform `makeCredential` with rpId `google.com` just fine — there is simply **no server endpoint to submit the result to**. Steps 1 and 3 of the three-step flow don't exist.
- Admin-side capabilities are policy and visibility only: enable passkeys/passwordless, restrict passkeys to hardware security keys only, enforce 2SV in "only security key" mode, and report on who has keys enrolled. The Admin SDK Directory API additionally allows turning 2SV off for a user and generating/invalidating backup verification codes — none of it registers a credential.
- Watch item: Microsoft and Okta both ship on-behalf APIs, so competitive pressure exists. Re-evaluate this section whenever Google announces admin passkey/security-key APIs.

### 7.2 What Blinky could still offer (prepare-only mode concept)

A `GooglePasskeyDirectory` with `Capabilities.SupportsRegistration = false, PrepareOnly = true` could deliver a meaningful subset without any Google write API:

1. **Key preparation job** (agent-only, no directory call): verify firmware/AAGUID against org policy, set a provisional FIDO2 PIN with `forceChangePin` where firmware allows, record serial ↔ cardholder assignment in inventory. The user's own Google enrollment later works with the pre-set PIN.
2. **Hand-off artifact**: generate a per-user instruction sheet (self-enrollment steps at `myaccount.google.com`, the one-time PIN delivered via the operator or existing secure channel) — reuse whatever document-generation pattern Blinky adopts.
3. **Compliance loop instead of registration confirmation**: via a service account with domain-wide delegation and read-only Directory API scopes, poll enrollment signals (2SV enrollment / security-key count per user) to flip the local state `Prepared → SelfEnrolledConfirmed`, and flag users who received a key but never enrolled. This replaces the `Registered` state; `Revoked` maps to "admin removes the key in the Admin console + Blinky marks locally" (no delete API assumed).
4. State machine variant for prepare-only: `Requested → KeyReady → Prepared → SelfEnrolledConfirmed | Lapsed` (+ `Failed`).

### 7.3 Pragmatic alternative to document

If the customer fronts Google Workspace with a federated IdP (Entra ID or Okta as the SAML/OIDC IdP for Google sign-in), provisioning the key at the IdP via Phase A/B gives phishing-resistant access to Google **without** Google-side enrollment. For many orgs this is the real answer; state it plainly in the docs so prepare-only mode is chosen deliberately, not by default.

### 7.4 Design obligations on Phases A/B (cost: near zero)

- `Capabilities` flags must include `SupportsRegistration` and `PrepareOnly` from day one (§4.1 already requires a capabilities model).
- The job contract must tolerate a provider-less "prepare" variant (ceremony steps without `Fido2CeremonyRequest`) — acceptable to model later as a distinct job type; just don't weld the PIN-policy step to the existence of creation options.
- The Angular provider selector renders unsupported/analysis-only providers as visible-but-disabled with a tooltip explaining why (transparency beats absence).

## 8. End-to-end sequence (identical for Entra and Okta)

```
Operator (Angular)      Blinky.Api              Provider API           Agent.Service        YubiKey
      │ create job ────────►│                                              │
      │                     │── Fido2PrepareRequest (SignalR) ────────────►│
      │                     │                                              │── HID probe ───►│
      │                     │◄─────────────── Fido2Ready ──────────────────│  (info, serial)
      │                     │── get creation options ─►│                   │
      │                     │◄── options (challenge) ──│                   │
      │                     │── Fido2CeremonyRequest (rp+origin) ─────────►│
      │  (status: touch)    │                                              │ setPin? ───────►│
      │                     │                                              │ makeCredential ►│ blink → touch, PIN
      │                     │◄──────────── Fido2CeremonyResult ────────────│
      │                     │── register attestation ─►│
      │                     │◄── method/factor id ─────│
      │◄─ result (+PIN once if ProvisionalRandom) ─ persist, audit, complete
```

Timing rule: elapsed time between fetching options and registering must fit the challenge TTL. Enforce a job-level deadline; on expiry, fail with a retryable code (and for Okta, delete the pending factor) — operator re-runs with a fresh challenge.

## 9. Security requirements

- Provider credentials (Graph app cert/secret, Okta token/private key) live in the existing secrets-at-rest store; never in logs. Prefer certificate/private-key-JWT over shared secrets.
- Provisional PIN: generated agent-side (CSPRNG, length ≥ policy min); with `ProvisionalRandom` shown to the operator exactly once in the UI, never persisted, never logged; with Okta `ProviderDelivers` it goes into the preregistration payload and is emailed by Okta — Blinky still never stores it. `forceChangePin` set whenever firmware supports it; if firmware lacks CTAP2.1, fall back to operator-set PIN and say so in the UI.
- Audit every step (job created, options issued, ceremony completed, registered at provider, revoked) with operator identity — reuse the existing audit trail; include `directoryProvider`.
- Treat a provisioned key as a live credential in transit; extend `docs/06-security.md` with shipping/chain-of-custody notes, mirroring the PUK-escrow threat notes.
- The FIDO2 PIN retry counter is independent of the PIV PIN — surface both distinctly everywhere (UI, inventory, error messages).

## 10. Error map (extend the existing error-mapping doc pattern)

| Source | Condition | Handling |
|---|---|---|
| CTAP2 | `CTAP2_ERR_CREDENTIAL_EXCLUDED` | Key already registered for this user → terminal, friendly message |
| CTAP2 | `CTAP2_ERR_PIN_BLOCKED` / `PIN_AUTH_BLOCKED` | Show retries, instruct reset flow (FIDO2 reset wipes all resident credentials — require explicit confirmation) |
| CTAP2 | `CTAP2_ERR_KEY_STORE_FULL` | No resident slots left → terminal, suggest key management |
| CTAP2 | user presence timeout | Retryable |
| Entra/Graph | 403 | Missing permission/consent → config error, actionable message |
| Entra/Graph | 400 policy-related (FIDO2 disabled / AAGUID not allowed / attestation rejected) | Terminal, map to §5 prerequisite hints |
| Okta | 401/403 (token scope) | Config error, actionable message |
| Okta | activation 4xx (policy, attestation, enrollment cap) | Terminal, map to §6.4 hints; delete pending factor |
| Okta | factor stuck `PENDING_ACTIVATION` | Cleanup: delete pending factor before retry |
| Both | 429/5xx | Retry with backoff (options fetch may need a fresh challenge) |
| Flow | challenge expired | Retryable with new challenge (Okta: after pending-factor cleanup) |
| HID | access denied / device vanished | Environment error; check LocalSystem, cable, key removal |

## 13. Known constraints to keep visible

- Entra Graph endpoints are **beta/preview**; Okta management API scopes and the Preregistration API's availability (possible EA flag) may shift — the abstraction and fixtures are the insurance.
- Entra: no B2B guests; UPN changes invalidate the method. Okta: Identity Engine only; per-user WebAuthn enrollment cap.
- **Google Workspace: no on-behalf registration API exists** — self-service enrollment only; §7 holds the full analysis, the prepare-only concept, and the federation alternative. Re-evaluate on any Google announcement of admin passkey APIs.
- Ceremony requires the physical key at the operator workstation; challenge TTL bounds ceremony duration.
- `forceChangePin` / `setMinPinLength` require CTAP 2.1 firmware — feature-detect via `AuthenticatorInfo`, never assume.
- rpId/origin are per-provider (and per-Okta-org) — any hardcoded `login.microsoft.com` outside `EntraPasskeyDirectory` is a bug.
